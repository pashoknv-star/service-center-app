## 3. Шаг данных `scripts/v6_director_data.sql` (на проде НЕ выполнялся)

Одна транзакция `BEGIN IMMEDIATE` (`:160`) … `COMMIT` (`:254`), `.bail on`, `.timeout 5000`; guard'ы в `CREATE TEMP TABLE v6_t` (`:166`) — NO-OP, если не выполнено хоть одно: ровно 1 «Костецкий…», 0 «Игнатенко…», есть `g3`, `schema_version ≥ 10`, должность «Директор» найдена или `pos_директор` свободен.

| Пункт ТЗ | Строки SQL | Как |
|---|---|---|
| ФИО и фото как раньше | `:196–202` (`UPDATE employees`) | без изменений по сути; + `group_id='g3'`, `updated_at` |
| Должность «Директор» | `:190–194` (создание), `:200` (назначение) | поиск `positions.name='Директор'` (при дублях — min `sort_order`, `id`); нет — `INSERT pos_директор`, `sort_order = MAX+1`; повтор — NO-OP |
| Очистка истории | `:239–243` | по `employee_id IN (SELECT id FROM v6_t)`: `schedule_entries`, `vacation_balances`, `trip_participants`, `trip_requests`, `task_assignees` (все роли и статусы) |
| tasks и trips не удаляются | `:231–236` | только `version+1` и `updated_at` у затронутых (устаревшие формы получат 409) |
| audit_log не чистится, запись о действии | `:205–218` | `employee.update` (+`position_id`) и `employee.history_clear` со счётчиками, актор `sql:v6-6` |
| sync_log | `:220–229` | `employee/upsert`; `entry/delete` на каждую удалённую запись графика (механизм есть: `entries.php`, `sync.php`); `trip/upsert` на затронутые командировки. Для `tasks` механизма sync нет |
| DRY-RUN | `:44–152` | matches, target already exists, g3, **«другие сотрудники g3» (ожидается 0) и их имена**, карточка с текущей должностью, **новая должность** (будет создана / найдена / КОНФЛИКТ), «УДАЛИТСЯ» по 5 таблицам (+ по статусам, ролям), «ОСТАНУТСЯ, version+1», командировки без участников, «станут «Без исполнителя»» — число и названия (только терминал) |

**Решение по id должности:** `pos_директор` (а не пример из ТЗ `pos_direktor`) — это ровно то, что даёт `positionSlug('Директор')` в `js/storage.js:261–265` (сьют `director` проверяет совпадение). С `pos_direktor` следующее сохранение из браузера (клиент пересобирает должности из названий ролей) создало бы второй «Директор» и переназначило бы сотрудника — дубль, который уже есть в dev-БД («Ведущий инженер», «Руководитель направления» ×2). Формат ТЗ «по правилам существующих записей» этим соблюдён (в dev-БД есть и латинские `pos_master`, и кириллические `pos_ведущий_инженер`).

**Ссылки на сотрудника в других таблицах** (проверено по `api/schema.sql` через `pragma_table_info`/`pragma_foreign_key_list` и по `db.php`): `schedule_entries`, `vacation_balances`, `trip_participants` (FK CASCADE), `task_assignees` (без FK, v10), **`trip_requests.employee_id`** (очередь RPA-заявок по участию в командировках; без FK) — решение «история очищена» → удаляется (заявка без участника не имеет смысла; иначе RPA-робот продолжил бы работать по очищенной командировке). `trips.created_by`/`tasks.created_by` — имена пользователей (`users`), не сотрудники; `users.scope_group_id` — группа; `audit_log.entity_id`/`sync_log.entity_id` — журналы (не чистятся по ТЗ). Других ссылок нет.

**Остаются без участников/исполнителей:** командировка, где он был единственным участником, останется без участников (список — в DRY-RUN; API `trips.php` при создании/правке требует ≥1 участника, но удалять командировки ТЗ запрещает; как UI рисует командировку без участников — не проверялось, командировки отложены, BL-01), задачи, где он был единственным исполнителем (станут «⚠ Без исполнителя»; число и названия — DRY-RUN, только терминал). Архивные/закрытые задачи теряют назначение молча (в ⚠ не попадают).
