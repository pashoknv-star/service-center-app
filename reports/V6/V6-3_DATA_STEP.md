## Что делает шаг

| Что | Значение |
|---|---|
| Кто | ровно один сотрудник с `full_name = 'Костецкий Андрей Николаевич'` (id в БД сохраняется) |
| ФИО | → `Игнатенко Павел Валерьевич` |
| Фото | `photo_url = 'images/photo_1794600000_d1ec7040.jpg'` (формат `api/upload.php`: `images/photo_<unix>_<8 hex>.<ext>`) |
| Группа | `group_id = 'g3'` (плитка «Управление СЦ») |
| Должность | «Директор»: берётся запись `positions` с `name = 'Директор'` (при дублях — с наименьшим `sort_order`, затем `id`); если такой нет — создаётся `pos_директор` (id по правилу `positionSlug` из `js/storage.js`: `pos_` + имя в нижнем регистре — тот же id даст браузер при следующем сохранении, дубля не будет; `sort_order` = MAX+1) и назначается сотруднику |
| **УДАЛЯЕТСЯ** (только строки этого сотрудника, по `employee_id`) | `schedule_entries` (отпуска, отгулы, больничные, командировки в графике и т. д. — все даты); `vacation_balances`; `trip_participants`; `task_assignees` (все роли — исполнитель и наблюдатель — и все статусы задач: открытые, закрытые, архивные); `trip_requests` (очередь RPA-заявок по его участию в командировках — единственная ещё одна таблица со ссылкой на сотрудника; остальные ссылки (`audit_log.entity_id`, `sync_log.entity_id`) — журналы, не чистятся) |
| **НЕ удаляется** | сами `tasks` (с чек-листами) и `trips`; `audit_log`, `sync_log`; прочие сотрудники и их данные. Задача, где он был единственным исполнителем, остаётся и показывается как «⚠ Без исполнителя» (`tasks.php?orphans=1`); командировка, где он был единственным участником, остаётся без участников (список — в DRY-RUN) |
| Служебное | `updated_at` сотрудника; у затронутых `tasks` и `trips` `version`+1 и `updated_at` (устаревшая открытая форма получит 409, а не вернёт удалённого исполнителя/участника); `audit_log`: `employee.update` (`{"changes":{…,"position_id":…}}`) и `employee.history_clear` (`{"deleted":{счётчики по таблицам}}`), актор `sql:v6-6`; `sync_log`: `employee`/`upsert`, `entry`/`delete` на каждую удалённую запись графика (формат `employee_id:date`, как у `entries.php`), `trip`/`upsert` на каждую затронутую командировку — открытые окна подтянут изменения дельта-синхронизацией. Для `tasks` механизма sync нет: список/счётчик ⚠ обновятся по событию сотрудника (`Tasks.onRemoteChange`) или по Ctrl+F5 |

Условия внутри SQL (при невыполнении — **ничего не меняется**, итог `NO-OP`): ровно 1 «Костецкий…»; «Игнатенко…» ещё нет (защита от дубля); группа `g3` есть; `schema_version >= 10`; должность «Директор» уже есть в `positions` либо id `pos_директор` свободен. Повторный запуск = `NO-OP` (после первого применения «Костецкий…» уже не находится).

### 4. DRY-RUN (счётчики; СТОП — только если цифры не совпали с ожиданием)
```bash
cd ~/v6-3
sed '/^-- @@APPLY/,$d' v6_director_data.sql | sqlite3 -readonly $WWW/data/app.db | tee ~/v6-dryrun.txt
```
Вывод — списком `колонка | колонка` (режим `list`, чтобы `sqlite3` 3.26 не обрезал длинные значения). Названия задач и ФИО печатаются **только в терминал** — в чат владельцу/в репозиторий их не копировать, достаточно чисел.

**Ожидаемые цифры (сверить построчно):**

| Строка вывода | Ожидается | Если иначе |
|---|---|---|
| `schema_version` | `11` | меньше 10 — APPLY откажется; довести миграцию |
| `matches (нужно ровно 1)` | **1** | 0 или >1 — **СТОП**, APPLY ничего не изменит; разобраться |
| `target already exists (нужно 0)` | **0** | >0 — **СТОП** (дубль) |
| `group g3` | `g3 \| Управление СЦ` | «В2С»/«Директор СЦ» — миграция v11 не отработала (шаг 2) |
| `другие сотрудники g3 (до APPLY; ожидается 0)` | **0** (владелец: «Другие сотрудники «В2С» — отсутствуют») | >0 — **СТОП**, показать владельцу строки `другой сотрудник g3` |
| карточка (`cur_position`) | текущая должность Костецкого — информативно | — |
| `новая должность «Директор»` | `pos_директор \| нет в positions — будет СОЗДАНА` **или** `<id> \| уже есть в positions (будет назначена)` | `КОНФЛИКТ: id pos_директор занят другим именем` — **СТОП** (APPLY был бы `NO-OP`) |
| `УДАЛИТСЯ: schedule_entries` / `vacation_balances` / `trip_participants` / `trip_requests` / `task_assignees` | числа и диапазон дат — информативно: это и есть объём очистки; цифры занести в отчёт о деплое | — |
| `ОСТАНУТСЯ, version+1: задач / командировок` | информативно | — |
| `командировок останется БЕЗ участников` | информативно (их `id`/название — ниже, только терминал) | — |
| `станут «Без исполнителя» (открытых задач)` | информативно: столько задач появится в «⚠ Без исполнителя»; названия — ниже, только терминал | — |

Ожидания по счётчикам удаления заранее неизвестны (боевых данных в репозитории нет); критерий СТОП — только первые пять строк с «ожидается». Если они совпали — переходить к APPLY.

### 5. APPLY (решения владельца получены; выполнять, если DRY-RUN совпал с ожиданием)
```bash
sqlite3 $WWW/data/app.db < ~/v6-3/v6_director_data.sql | tee ~/v6-apply.txt
# в конце вывода: «APPLIED: 1 сотрудник обновлён, история очищена»; «удалено: …» по таблицам (те же числа, что в DRY-RUN);
# «остаток Костецкий… = 0»; «история Игнатенко… везде 0»; foreign_key_check пуст; integrity_check = ok
```
Один запуск = одна транзакция (`BEGIN IMMEDIATE … COMMIT`, `.timeout 5000` — ждёт блокировку до 5 с при параллельной записи PHP, `.bail on`: при любой ошибке транзакция откатывается, БД не меняется).

**После APPLY: Ctrl+F5 во всех открытых окнах** (матрица в уже открытых окнах не перерисовывается сама — до смены года показывала бы старое ФИО/отпуска; плитка зоны, Доска и счётчик ⚠ обновляются сами).
