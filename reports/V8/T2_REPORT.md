## Найденные дефекты (подробно)

- **D-1 (P1 для очереди) — заявки теряются молча.** `generateRequestId()` (`api/helpers.php:118–121`) строит `'SC-' . substr($tripId, 0, 4) . '-' . n . '-' . time()`; `substr($tripId,0,4)` у **всех** trip = `trip`, значит у двух командировок, подтверждённых в одну секунду, `request_id` одинаков (PRIMARY KEY, `api/db.php:250–251`). INSERT падает, общий `catch` очереди (D1, `api/trips.php` `:731–734`) проглатывает ошибку, а командировка остаётся `confirmed` **без заявок** (и остальные участники этого confirm тоже теряют заявки — `catch` вне `foreach`). Воспроизведено на старом коде: 6 командировок подряд → заявок `[2,0,0,0,0,0]`. Исправлено локально в confirm (`api/trips.php:701–719`): при занятом `request_id` добавляется суффикс от `trip`; префикс `SC-trip-<n>-<время>` для робота и `helpers.php`/`trip_relay.php` не тронуты. Тест: «6 подряд → по 2 заявки, 12 разных id, формат сохранён».
- **D-2 (P2) — supervisor не видел «Удалить»/«Подтвердить» у своих командировок в реальном браузере.** `canDeleteTrip` (`js/trips.js:2425`, строка сравнения `:2433`) сравнивал `String(e.id) === String(p.employeeId)`, а `window.__serverEmployees` отдаёт числовые id (`'2'`), участники — `emp_2`. Зона не находилась → fail-closed (форма read-only, кнопка скрыта), юнит-тест hygiene этого не ловил (мок с `emp_N`). Исправлено сравнением по `normEmpId`; тест: supervisor видит «Удалить» у прогноза своей зоны, у чужой — нет. Побочный эффект (улучшение): supervisor снова видит «Удалить» у прогноза своей зоны.
- **D-3 (тест T1).** `tripsform` (`scripts/test_trips_v8_form.js:156`): серверная проверка payload робота подтверждает командировку без места — теперь она создаётся с `location:'Казань'` (confirm требует место, п.7). Другие проверки сьюта не менялись (99/99).
- **Наблюдение без правки (риск).** Обычные `POST`/`PUT` принимают `status:'confirmed'` без заявок, без проверки места и без `confirm`-пути (`api/trips.php` POST `:434`, PUT `:790`) — только руками собранным запросом, форма его не шлёт (при правке `status` не передаётся). По границам задачи не менял; закрыть (`400 use_confirm_action` для forecast→confirmed вне `action=confirm`) — решение координатора.
