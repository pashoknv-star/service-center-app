# БФТ: блок «Задачи» (task-block) — v1.0 УТВЕРЖДЁН владельцем 2026-11-07

Статус: УТВЕРЖДЁН (в т.ч. допущения Д-1..Д-4). Следующий документ — ТЗ (`TZ.md`), затем Kanban.
Roadmap: добавлены T1 («актуально») и T2 («отложено»), резервная копия сделана; отметка «выполнен» — только после приёмки владельцем.

## 1. Цель
Простой блок задач, закреплённых за сотрудниками, привязанный к календарю и синхронизированный с матрицей (отпуск, больничный, командировка, выходные, праздники). Ориентир — Trello/Outlook без перегруза.

## 2. Принцип разделения
- Детерминированное (PHP API + n8n): CRUD, права, даты, проверка конфликтов, расчёт «первого дня», индикация.
- LLM (узкая аналитика; только предлагает, запись в БД после подтверждения человека): разбор текста в черновик, анализ загрузки, дайджест, предложение приоритета/метки.

## 3. Роли и доступ (MVP)
| Роль | Видит блок «Задачи», иконки, карточки | Создаёт / правит / назначает / закрывает |
|---|---|---|
| admin | да | да |
| supervisor | да, только чтение | нет |
| viewer | да, только чтение | нет |

Видимость глобальная (по аналогии с E8-4): supervisor/viewer видят иконки и задачи всех сотрудников. Исполнители отдельной ролью не являются: исполнитель — сотрудник матрицы, на которого назначена задача.
**Итерация 2 (T2, в роадмап):** supervisor/viewer получают право менять статус на «Закрыта» + уведомления (Telegram, in-app, e-mail) + комментарии, история, вложения.

## 4. Функциональные требования (MVP)
- **FR-01 Задача:** название; описание; исполнитель(и) 1..N; срок ИЛИ период (дата+время); приоритет (3 уровня); метка; чек-лист.
- **FR-02 Исполнители:** 1..N; переназначает admin; поле «наблюдатель» хранится, но не используется до итерации 2 (видимость/уведомления).
- **FR-03 Статус:** «открыта» / «закрыта»; меняет только admin; admin может переоткрыть.
- **FR-04 Срок/период:** одна точка во времени либо начало–конец.
- **FR-05 Иконка в календаре:** в ячейке дня сотрудника — только на ПЕРВОМ дне срока/периода и только у ОТКРЫТОЙ задачи. Закрытая задача иконку не показывает. Выбран вариант B (кружок со счётчиком открытых задач, стартующих в этот день).
- **FR-06 Рамка срока:** весь срок (все дни периода) выделяется тонкой рамкой по образцу обрамления фото сотрудника в зоне (цвет `--rt-blue` #0088CC, скруглённая, без заливки). Для срока в один день рамка вокруг одной ячейки.
- **FR-07 Переход:** клик по иконке открывает панель «Задачи» в режиме «неделя/день» (как Outlook) на выбранном сотруднике и дне, с описаниями. Supervisor/viewer открывают эту панель в режиме чтения.
- **FR-08 Представления** (макеты `mockups.html`): основной вид панели — 2.2 «Список»; клик по фамилии или задаче в списке → 2.1 «Доска» (по фамилии: доска выбранного сотрудника; по задаче: доска с выделенной карточкой); переключатель на 2.3 «Календарь» показывает ВСЕ существующие задачи всех сотрудников, внутри плитки — ФИО и описание.
- **FR-09 Синхронизация с календарём:** задачи в реальном времени читают из матрицы отпуска, больничные, командировки, выходные, праздники.
- **FR-10 Правила конфликтов:**
  | День исполнителя | Правило |
  |---|---|
  | выходной, праздник, отпуск | задача МОЖЕТ охватывать эти дни; на карточке нейтральная пометка, без запрета и без подсказок |
  | больничный, командировка | задача НЕ МОЖЕТ охватывать эти дни: сохранение блокируется, система предлагает ближайшую дату вне блокирующих дней, admin подтверждает |
  Проверяется каждый день срока/периода, по каждому исполнителю.
- **FR-11 Позднее появление больничного/командировки** над уже существующей открытой задачей: запись матрицы НЕ блокируется (уроки ИНЦ-1/2); задача получает признак «конфликт» (вычисляется при чтении, не хранится) — красная пометка в панели и на иконке; admin переносит или переназначает.
- **FR-12 Аудит:** все мутации задач — в audit_log.

## 5. Архитектура / n8n
- Итерация 1 — вариант B: приложение = хранение, CRUD, права; n8n = детерминированные правила (проверка конфликтов, подбор ближайшей даты, пометка «конфликт» по расписанию) через webhook. Если неудобно — вариант C; если неудовлетворительно — гибрид.
- Уведомления, комментарии/история/вложения — итерация T2.
- Ограничение MCP: Hermes↔n8n даёт только search/get/execute workflow; создание workflow — импорт JSON в n8n владельцем или API-ключ n8n (решение владельца). Сейчас на сервере n8n 0 workflow.

## 6. LLM
Все четыре функции (текст→черновик; загрузка; дайджест; приоритет/метка). Данные: фамилии и тексты задач — да; телефоны, фото, пароли, токены — нет. Ответ LLM — только предложение. Масштаб до ~50 сотрудников. Порядок внутри T1: ядро → n8n → LLM.

## 7. Нефункциональные требования
- Отдельный `api/tasks.php`, не через sync-delete `save.php`; версионирование записи (optimistic) от устаревшей вкладки.
- Часовой пояс +05.
- HTTP (BL-02): токен n8n передаётся открытым текстом — риск принят до HTTPS.
- Деплой только по «Деплой»; после фазы стоп до «Старт».

## 8. Допущения координатора (принимаются, если не возражаете)
- Д-1. Правило «больничный/командировка» применяется к каждому дню периода (не только к первому).
- Д-2. Несколько исполнителей: иконка и рамка — в строке каждого исполнителя; конфликты — по каждому отдельно.
- Д-3. Если n8n недоступен при сохранении (таймаут 3 с): задача сохраняется с признаком «не проверено», повторная проверка по расписанию; в UI видна пометка. Fail-closed не применяем, чтобы n8n не парализовал работу.
- Д-4. Удаление задачи — только admin, мягкое (в архив).

## 9. Закрытые вопросы

## 10. Решения владельца 2026-11-07
- Иконка: вариант B. Основной вид: список → доска → календарь (FR-08).
- Интеграция n8n: владелец выдаёт API-ключ n8n (ключи в файлы и чат не помещаются; хранение — vault/env, см. ТЗ §9).
- LLM: модель и ключ предоставит владелец.
