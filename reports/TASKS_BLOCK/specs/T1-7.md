# T1-7 D-1 backend: задача остаётся при удалении сотрудника («исполнитель удалён»)
Прочитать `00_COMMON.md`, `T1-1_REPORT.md`, `T1-6_ACCEPTANCE.md` §6 D-1. Зависит: T1-9 принят. Исполнитель — автор T1-1.

## Решение владельца (2026-11-10, дословно по смыслу)
Сотрудника удалять; его задачу оставлять без исполнителя с визуальным отображением; после удаления предлагать замену (модальное окно — это T1-8, UI).

## Дефект сейчас
`task_assignees.employee_id REFERENCES employees(id) ON DELETE CASCADE` (`api/db.php:301`, `api/schema.sql:254`): любое удаление сотрудника (UI → sync-delete `api/save.php`, `api/employees.php` DELETE, полная очистка `api/import.php:55`) молча стирает назначения, задача остаётся с `assignees:[]`.

## Решение (обязательная схема)
1. Миграция v9→v10 в `api/db.php` (+ `api/schema.sql`): пересобрать `task_assignees` БЕЗ FK на `employees` (FK на `tasks` с CASCADE сохранить), добавить колонку `full_name_snapshot TEXT` и заполнить её из `employees` при миграции. Пересборка таблицы по правилам SQLite (create new → copy → drop → rename) в транзакции, идемпотентно, с учётом `foreign_keys` (см. комментарий `api/db.php:123`). Существующие данные не терять.
2. `full_name_snapshot` пишется при каждом назначении (POST/PUT задачи) и обновляется при переименовании сотрудника — путь, где меняется `full_name` (`employees.php` PUT и sync-путь `save.php`), минимальной вставкой.
3. Пути удаления (`save.php`, `employees.php`, `import.php`) НЕ меняются по логике удаления: назначения просто остаются. Если импорт вернул сотрудника с тем же id — назначение восстанавливается само.
4. «Удалён» вычисляется при чтении: исполнитель, чьего `employee_id` нет в `employees`.
   - В ответах `api/tasks.php` (список и карточка) каждый элемент `assignees[]` получает `removed: true|false`; у удалённого `full_name` = snapshot.
   - У задачи — `orphan: true`, если НЕТ ни одного действующего исполнителя (у задачи с 2 исполнителями, где удалён один, `orphan:false`).
   - `removed_at`: дата из последней записи `audit_log` `employee.delete` по этому id (или `null`, если нет).
5. Новые чтения (admin/supervisor/viewer — как прочие GET):
   - `GET api/tasks.php?orphans=1` → открытые неархивные задачи с `orphan:true` (без фильтра периода) — для счётчика ⚠ и фильтра «Без исполнителя».
   - `GET api/tasks.php?open_for=<employee_id>` → открытые неархивные задачи, где сотрудник — действующий исполнитель: `{count, tasks:[{id,title,start_at,end_at,version}]}` — для подтверждения и модального окна до удаления.
6. Правила записи для задач с удалённым исполнителем:
   - close / reopen / archive разрешены и для `orphan`-задачи;
   - PUT без изменения `assignees` (текст, приоритет и т.п.) разрешён, удалённые исполнители остаются как есть;
   - PUT с `assignees` — только существующие сотрудники (`employee_not_found` для удалённых id), с обычной проверкой sick/trip → 422 + `suggested_start` (FR-10). Переназначение = замена удалённого на нового;
   - удалённый исполнитель не участвует в проверке sick/trip, conflict, n8n validate/recheck (фактов по нему нет).
7. Аудит: в `employee.delete` (оба пути — `employees.php` и `save.php`) дописать в details `open_tasks: [task_id…]` — открытые задачи, где он был исполнителем. Переназначение пишется обычным `task.update`.
8. Матрица: задачи удалённого сотрудника в матрице не рисуются (строки нет) — поведение `js/tasks_matrix.js` не менять; проверить, что `orphan`-задачи не ломают её (нет исключений по отсутствующему сотруднику).
