# T1-5 LLM-функции (4 workflow) + подтверждение в UI
Прочитать `00_COMMON.md`, TZ §5. Зависит: T1-3 и T1-4 приняты.

PRECONDITION: модель и ключ LLM выданы владельцем и заведены в n8n credentials/окружение (значения НЕ печатать, не писать в файлы). Если нет — `kanban block`.

Objective: узкие аналитические функции; LLM только предлагает.

Workflow (n8n, создаются через REST API; JSON в `n8n/` без credentials):
1. `llm-draft`: свободный текст («Петрову подготовить отчёт до пятницы 15:00») → JSON-черновик полей задачи. Сопоставление фамилий с `employee_id` — детерминированно (в n8n), LLM только извлекает сущности.
2. `llm-load`: анализ загрузки по детерминированно посчитанным данным (число открытых задач, дни отсутствия) → рекомендация исполнителя.
3. `llm-digest`: дайджест для admin (просрочено, риски) по детерминированно посчитанному набору; в T1 — показ в панели, без рассылки.
4. `llm-label`: предложение приоритета и метки по тексту.
Требования: вход LLM — только фамилии и тексты задач и обезличенные счётчики; телефоны, фото, пароли, токены не передаются (allowlist полей на входе workflow); выход валидируется по JSON-схеме, при невалидном — отбрасывается; запись в БД — только через `api/tasks.php` после явного подтверждения admin в UI (кнопки «Применить»/«Отклонить»); таймаут и безопасный отказ (панель работает без LLM). UI-часть — минимальная, `js/tasks.js` (точечно) и точечные вставки index.html только если необходимо.

Acceptance: AC-9 (тест, что payload не содержит запрещённых полей — проверка на реальных исполнениях n8n, привести фактические payload без секретов); для каждой из 4 функций — пример исполнения с реальным ответом; невалидный ответ LLM не пишется в БД; `verify_all.sh` → GATE: PASS.
Artifacts: `n8n/*.json`, код UI, тесты, `T1-5_REPORT.md`, коммит.
