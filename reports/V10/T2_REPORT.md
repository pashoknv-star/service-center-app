## 6. Допущения и неоднозначности контракта (для addendum/решения координатора)

Тесты по возможности терпимы к неоднозначности (проверяют только то, что контракт гарантирует); ниже — где я сделал выбор. «Тест» — какие проверки затрагивает выбор.

1. **Обёртка ответов** не зафиксирована (`{success, request}`? плоский объект?). Хелперы принимают и `{request:{…}}`, и плоский объект с `id`; список — `requests`/`items`/голый массив. Предлагаю в addendum: `request`, `requests`, `assignment` (как у T1: `base`, `vehicle`).
2. **Список заявок:** тесты считают `from/to/status` необязательными; `from/to` фильтруют по дням назначений (заявка с назначением в диапазоне попадает, вне — нет; R21, P11). Что делать с заявками **без** назначений при `from/to` — контрактом не определено (не проверяется).
3. **`PUT` без `version`** → принято `422 version_required` (по аналогии с T1/`api/tasks.php`); контракт для заявок/назначений код не называет (R7, A8).
4. **Пустой `title` и неизвестный `status`** → проверяется только 422 и непустой `error` (кода в контракте нет; R3, R19).
5. **Длительность:** текст задачи упоминает «`invalid_step` для длительности», контракт (строка про время) даёт `invalid_duration` для `duration_min` и `invalid_step` только для `stay_min`/`leg_min`. Принят **контракт** (S6–S8 → `invalid_duration`; S9–S11 → `invalid_step`).
6. **Таблица переходов** контрактом не дана («T5 фиксирует в отчёте»). Проверены только однозначные: `new→cancelled`, `cancelled→new`, `assigned→in_progress→done→new`, **ручной `new→assigned` → `invalid_transition`**, `cancelled→in_progress/done` → `invalid_transition`. Не проверены (T5 решает и фиксирует): `new→in_progress/done`, `assigned→new`, `in_progress→new`, `done→cancelled`, `X→X`, судьба назначений при отмене/возврате, правка полей `done/cancelled` заявки.
7. **Журнал заявок/назначений:** контракт T1 называет действия только для справочников. Тесты находят записи по `entity_id` (id заявки/назначения) и проверяют: `before_json` NULL при создании; `after_json` NULL при удалении; `action` соответствует `/create|add|new/`, `/update|edit|change/`, `/delete|remove/`; `entity_type` непуст и у заявки ≠ у назначения; `actor` = `users.id` или логин; `role` = `admin`/`supervisor`; `warnings_json` — массив с кодами. Предлагаю зафиксировать: `request.create|update|status`, `assignment.create|update|delete`, `entity_type` = `request`|`assignment`. Количество записей проверяется строго только для «своей» сущности (ровно одна на мутацию); автосмена статуса заявки при создании/удалении назначения может писать отдельную запись или нет — тесты от этого не зависят (как и от роста `version` заявки при автосмене).
8. **`dry_run`** → HTTP 200 `{success, warnings:[…]}`; `confirm_token` проверяется только при непустых предупреждениях. Ответ 409 на отсутствие/неверный токен — `confirmation_required` с `warnings` (буквальное «иначе» контракта: чужой, мусорный, пустой, нестроковый токен — тот же 409).
9. **Токен привязан к набору кодов** (W25, W26): токен для `[vehicle_overlap]` не годится для `[vehicle_overlap, route_sum_mismatch]` и наоборот; привязка к конкретному содержимому запроса/ID конфликтующих назначений тестами не требуется и не запрещается.
10. **`DELETE` назначения** → `200 {success:true}` (не 204; контракт код успеха не называет). `PUT` назначения принимает полное тело (с `request_id`, неизменным) + `version`.
11. **Отсутствия:** `driver_absent`/`crew_absent` — `schedule_entries.status ∈ {vacation, sick}` и подтверждённая командировка (`trips` + `trip_participants`, период включительно). Не тестируются: `day_off`, статус `trip` в `schedule_entries` (legacy), командировка `forecast`, `approval_status` (фикстуры — `approved`). Назначение покрывает дни от даты `start_at` до даты момента `end_at − 1 мин`: переход через полночь (W17) затрагивает оба дня; точное попадание `end_at` ровно на 00:00 не проверяется.
12. **Пересечения:** учитываются назначения других заявок; назначения заявок в `cancelled`/`done` в тестах не фигурируют — **вопрос**: должны ли они считаться занятостью (я бы предложил «нет», но контракт молчит). Совмещение ролей (водитель одного назначения — член бригады другого в то же время) не проверяется.
13. **Маршрут:** `stops` передаётся всегда (`ord` с 1; выезд/приезд, сумма `stay_min + leg_min` = `duration_min`, иначе `route_sum_mismatch`); отсутствие `stops` и 0 точек не проверяются. `leg_min_map` — только в сохранении (A10), без проверки шага.
14. **Необязательные поля**: `source` проверяется один раз со значением `manual` (R2); `created_by_name` — непустая строка; формат `display_no` не проверяется (непустой, уникальный, не меняется при правке; в т.ч. при параллельном создании, C6).
15. **Неизвестный водитель** (нет такого сотрудника): допускается `driver_not_allowed` или `unknown_employee` (D4).
16. **`transport_warnings.php`**: HTTP-контракта нет (в `CONTRACT.md` предупреждения — внутри `POST/PUT assignments`), отдельного теста нет; сьют проверяет предупреждения через публичный интерфейс.
17. **Не покрыто (вне зоны T2/T5 по контракту):** строки сводной таблицы «Читать доску» (`transport_board.php`) и «Журнал (чтение)» (`transport_journal.php`) — это T6, фаза B; включение их в `transport` сделало бы сьют недостижимым для T5. Предлагаю тесты T6 добавить отдельным сьютом/addendum.

## 7. Заметки для T5 и приёмки

* **Падение PDO:** `PDO::inTransaction()` возвращает **false** после ручного `$pdo->exec('BEGIN IMMEDIATE')` (проверено на PHP 8.3.6: `exec('BEGIN IMMEDIATE')` → `false`, `beginTransaction()` → `true`). Если T5 защитит `COMMIT/ROLLBACK` условием `inTransaction()`, коммит молча не произойдёт (данные пропадут на конце скрипта; в моём прототипе именно так и вышло). Нужен собственный флаг «транзакция открыта». Тесты J9–J11 и C1–C3 такие ошибки ловят.
* **Сессии PHP блокируют:** два запроса одной cookie-банки сериализуются (`session_start()` держит блокировку файла сессии). Для настоящей гонки тесты используют разные сессии (`admin`/`admin2`/`z0`/`z1`).
* **Гонки:** C1–C3 запускают 2–3 одновременных запроса на 4 обработчиках `php -S`, по 3–5 раундов. Корректная реализация с `BEGIN IMMEDIATE` всегда проходит; реализация без блокировки краснеет не в каждом раунде, но повторными раундами вероятность пропуска мала.
* **Окружение:** требуется CLI `php` с `PHP_CLI_SERVER_WORKERS` (PHP ≥ 7.4, не Windows), `curl` (расширение), `pdo_sqlite`. Время прогона на прототипе ≈ 20 с.
* Фикстуры T1 по контракту: `POST entity=base|vehicle` → 201 с `base.id`/`vehicle.id`/`vehicle.version`; `POST entity=pool` → 200|201; `DELETE entity=pool&id=` → 200; `PUT entity=vehicle` с `version`; `GET` → `bases/vehicles/drivers[{employee_id,name,source}]` без `phone`/`photo`; `POST action=move`. Если T1 реализует иначе (имя ключа, код успеха), расхождение вернётся addendum-задачей ко мне.
