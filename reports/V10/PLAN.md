## 3. Модель данных (schema v15)

- `transport_bases(id, name UNIQUE, sort_order)`.
- `vehicles(id, name, plate UNIQUE, base_id, status in_service|repair, default_driver_id, sort_order, version, …)`.
- `transport_driver_pool(employee_id TEXT PRIMARY KEY → employees.id, added_by, added_at)` — совместители, имеющие право управлять ТС.
- `transport_requests(id, display_no, title, subscriber, address, comment, status new|assigned|in_progress|done|cancelled, source, external_id, version, created_by, …)` — без `zone_id`.
- `transport_assignments(id, request_id, vehicle_id, driver_id, driver_name_snap, start_at, duration_min CHECK %15, end_at, override_json, version, …)`; индексы по `(vehicle_id,start_at,end_at)` и `(driver_id,start_at,end_at)`.
- `assignment_crew(assignment_id, employee_id, name_snap)`.
- `assignment_stops(assignment_id, ord, kind departure|intermediate|arrival, place, lat, lon, stay_min, leg_km, leg_min_map, leg_min)` — `leg_min_map` — предложение карты, `leg_min` — принятое значение; оба кратны 15.
- `geo_cache(key, kind, payload_json, fetched_at)`.
- `transport_journal(id, ts, actor, role, action, entity_type, entity_id, before_json, after_json, warnings_json)` — append-only; пишутся и переносы ТС, и изменения списка совместителей.

## 7. Что осталось подтвердить

1. **Право переноса ТС у viewer.** В сообщении сказано «Viewer… перемещает ТС между базами»; фиксирую буквально. Это нарушает прежнее правило «наблюдатель ничего не пишет» (`docs/ROLES.md`) и вынесено в отдельный эндпоинт. Если это опечатка — достаточно убрать viewer из проверки в T1 (одна функция) и из тестов T2.
2. **Supervisor не переносит ТС** (в списке прав его нет) — оставлено так.
3. **Журнал читает только admin** (в требованиях не уточнено).
4. Для поиска на карте уходит только название населённого пункта, без улицы; адреса и улицы наружу не передаются.
5. Решение по провайдеру маршрутов — после T4.

Уточнение при запуске фазы A: T1 пишет собственный сьют `transportdb` (схема, ТС, базы, пул, перенос, журнал; красный прогон до кода), T2 — сьют `transport` под T5 (заявки, назначения, предупреждения, роли). Фикстуры T2 строятся через API T1 по `specs/CONTRACT.md`; после слияния T1 координатор прогоняет T2 против реального API.
