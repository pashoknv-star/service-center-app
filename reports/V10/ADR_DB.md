# ADR_DB — V10 «Транспорт»: SQLite или PostgreSQL

**Вердикт (релиз 1): ОСТАЁМСЯ НА SQLite — рекомендация координатора подтверждена числами, но с тремя обязательными условиями.**
1. Все записи модуля, где «проверил пересечение → записал», — только в `BEGIN IMMEDIATE`. Текущий шаблон проекта (`PDO::beginTransaction()` = отложенный `BEGIN`, 18 мест в 10 файлах) для этого **не годится**: на замере при ≥2 писателях 61–85 % операций (WAL; 17–52 % в DELETE) падает с `SQLITE_BUSY` сразу, не дожидаясь `busy_timeout` (§2.2). Без транзакции — 31–42 нарушения (пересечения ТС, пропущенные проверкой) на 150 операций/писатель (§2.2).
2. Триггеров `BEFORE UPDATE/DELETE` (`specs/CONTRACT.md:41`) **недостаточно**: `INSERT OR REPLACE` / `REPLACE INTO` с существующим `id` переписывает запись журнала мимо обоих триггеров (воспроизведено, §5). Нужен третий триггер `BEFORE INSERT … WHEN NEW.id уже есть` (проверен, закрывает обход).
3. Размер и нагрузка прод-БД **неизвестны** — числа §3 для «нашего» профиля это допущения; владелец снимает размер командой из §3.4 и сверяет с порогами §6.

Условия замеров (если не сказано иное): dev-машина, PHP 8.3.6 CLI, SQLite 3.45.1, 2 vCPU, ext4, копия `data/app.db` (1 589 248 байт, sha1 `a2e65ae4…5d6d` **до и после** всех прогонов; `data/app.db` не открывался на запись). Прод (Hostland): web-PHP 8.1.34, `sqlite3` CLI 3.26 (`DEPLOY_HOSTLAND.md:11,20`) — **на проде числа не снимались**, ниже на этот счёт везде пометка.

Сырые выводы — `reports/V10/T3_evidence/` (A…K); скрипты — `scripts/spike/v10_t3_*` (одноразовые, в gate не входят). Код приложения не менялся.

## 2. Параллельная запись (замер)

### 2.1 Методика
Скрипт `scripts/spike/v10_t3_concurrency.php`. N процессов PHP одновременно (барьер старта по `hrtime`) выполняют по `ops` операций; **каждая операция — новое соединение + PRAGMA в порядке `api/db.php:724-726`** (на проде соединение живёт один запрос). Операция = «проверить пересечение ТС по времени (`SELECT COUNT(*)`) → пауза `work-ms` (имитация логики, окно гонки) → `INSERT` назначения → `INSERT` журнала → фиксация». Половина операций (`--contest=0.5`) — «спорные»: все писатели целятся в один слот одного ТС (ровно один должен победить, остальные получают законный отказ `confl`); половина — приватные (свой ТС).
Режимы транзакции: `none` — автокоммит; `deferred` — `BEGIN` (ровно `PDO::beginTransaction()` проекта); `immediate` — `BEGIN IMMEDIATE`. Режимы журнала: `wal` и `delete` (один и тот же сценарий). Транспорт: `proc` — отдельные процессы PHP; `http` — через `php -S` с `PHP_CLI_SERVER_WORKERS=max(2,N)` (`concurrency.php:347`).
Столбцы: `ok` — вставлено; `confl` — законный отказ по пересечению; `busy` — операция провалилась с `SQLITE_BUSY` (кода 5/6); `busy%` — доля операций с BUSY; `viol` — **нарушения**: пары пересекающихся интервалов одного ТС, оказавшиеся в БД; `noJ`/`orphJ` — назначения без журнала / журнал без назначения (все 0).
Только `busy_timeout=5000` — как в проде; повторов нет (кроме прогона B). Операции идут впритык, без пауз «на размышление»: это **насыщение**, а не реальная нагрузка (реальная — §2.5).

Цена — очередь: p95 ≤ 127 мс, но p99 до 0,94 с (WAL) / 1,75 с (DELETE) и максимум 2,3 с / 4,2 с при N=8 впритык. - Журнал целостен всегда (`noJ`=`orphJ`=0): запись назначения и журнала в одной транзакции атомарна даже при гонке.

### 2.5 Что это значит для реальной нагрузки
Измеренный потолок ≈ 60–100 коммитов/с при насыщении 2–8 писателями. Допущение §3 (до 200 заявок/сут × ~8 записей журнала, один коммит на действие) даёт ≈ 1 600 коммитов/сутки ≈ **0,02 коммита/с в среднем**; даже пик ×100 (2 коммита/с) — на два порядка ниже потолка. Одновременных писателей в проекте — единицы (4 водителя + совместители — `PLAN.md:14`; диспетчеров — несколько: число **неизвестно**, допущение ≤ 4). ## 4. Бэкап и откат

**Как сейчас (SQLite, Hostland):** один файл. **Что менялось бы при PostgreSQL:**
- Отдельный сервер БД вне Hostland-пакета (расширения `pdo_pgsql` в списке нет — `DEPLOY_HOSTLAND.md:13`; доступ к серверу не подтверждён): учётные данные, сетевая задержка на каждый запрос (в SQLite — вызов в процессе), хранение секретов в конфиге вместо файла.

## 5. Журнал без очистки на SQLite: достаточно ли триггеров

Скрипт `scripts/spike/v10_t3_journal_triggers.php` (временная БД в `$TMPDIR`, `data/app.db` не открывается; DDL — дословно `specs/CONTRACT.md:41`; PHP 8.3.6, SQLite 3.45.1; вывод `H_journal_triggers.txt`, повторный прогон дал тот же результат). `recursive_triggers=OFF` — как в проде (`db.php:724-726` его не включает).

**Закрыто триггерами `BEFORE UPDATE`/`BEFORE DELETE → RAISE(ABORT)`** (6 проб — `SQLSTATE 23000 … transport_journal is append-only`, данные не изменены): `UPDATE` одной/всех строк, `DELETE` одной/всех строк (в т.ч. без `WHERE`), `INSERT … ON CONFLICT(id) DO UPDATE`, `UPDATE OR REPLACE`. Из `sqlite3`-CLI те же триггеры тоже срабатывают (триггеры хранятся в файле БД): `Error: stepping, transport_journal is append-only (19)`.

**НЕ закрыто — найдено, реально для приложения:** `INSERT OR REPLACE INTO transport_journal (id, …)` и `REPLACE INTO …` с существующим `id` **выполняются** и переписывают запись (проверено: содержимое записей заменено на `FORGED`, `H_journal_triggers.txt` блок A). Причина: REPLACE удаляет старую строку без вызова `BEFORE DELETE`, пока `recursive_triggers=OFF`. Включение `recursive_triggers=ON` закрывает дыру (проба B), но это глобальная настройка соединения, меняющая поведение триггеров всего проекта — не рекомендуется. **Рекомендуемое усиление (проба C, обход закрыт, штатная вставка без `id` проходит):**
```sql
CREATE TRIGGER transport_journal_no_replace BEFORE INSERT ON transport_journal
WHEN NEW.id IS NOT NULL AND EXISTS (SELECT 1 FROM transport_journal WHERE id = NEW.id)
BEGIN SELECT RAISE(ABORT, 'transport_journal is append-only'); END;
```
Плюс правило кода: `transport_journal_write` — единственное место вставки, `id` не передаётся (`CONTRACT.md` описывает `transport_journal_write`). *На момент отчёта в worktree T1 (`/home/hermes/wt/v10-t1`, не закоммитано) есть только два триггера (`api/schema.sql:457-463`, `api/db.php:536-542`) — требуется добавление третьего; передать координатору как правку к T1, я чужие worktree не менял.*

**Остаточные обходы (все требуют права записи в файл БД или выполнения произвольного SQL):**
| Способ | Результат пробы | Реальность на Hostland |
|---|---|---|
| `DROP TRIGGER` → `UPDATE`/`DELETE` | выполнено (ОБХОД) | Нужен произвольный SQL. В коде приложения эндпоинта «выполнить SQL» не искал и не нашёл в рамках этой задачи (полный аудит инъекций не проводился); путь — либо SSH-доступ к файлу (логин описан в `DEPLOY_HOSTLAND.md:16`, пароль у владельца — `AGENTS.md`, «Security and side effects»), либо уязвимость SQL-инъекции. Реалистично: владелец/доверенный админ, не обычный пользователь приложения |
| `DROP TABLE transport_journal`; `ALTER TABLE … RENAME` | выполнено (триггеры `DELETE` не вызываются) | то же |
| `PRAGMA writable_schema=ON; DELETE FROM sqlite_master WHERE type='trigger'` | выполнено (SQLite 3.45 без `SQLITE_DBCONFIG_DEFENSIVE`) | то же |
| Прямая правка файла `app.db` (hex/другая программа) / подмена файла | не ограничивается ничем | Файл доступен веб-пользователю на запись (ACL, `DEPLOY_HOSTLAND.md:18`) и SSH-пользователю; закрыт от HTTP (`Require all denied` на `data/`, `:14,45`, проверка `curl /data/app.db → 403`, `:198`). Угроза — компрометация аккаунта хостинга/уязвимость загрузки файлов, а не обычный пользователь |
| `.restore` из старого бэкапа | журнал откатывается (§4) | владелец при откате |

**Обнаружение (не предотвращение) подмены**, проверено пробой F: цепочка хешей `row_hash = sha256(prev_hash | ts | actor | action | entity | after_json)`. Разрыв цепочки ловит `UPDATE` и `DELETE` в середине; **не ловит удаление хвоста** — нужен внешний якорь (последний `row_hash` вне файла БД: письмо владельцу/файл в `backups/`/Telegram-сводка). Стоимость: колонка `row_hash` + вычисление внутри уже существующей `BEGIN IMMEDIATE`-транзакции (запись и так сериализована); изменение схемы T1 (addendum), **решение владельца**, в релизе 1 не обязательно.

**Вывод по п.5:** для требования владельца «правка и удаление записей запрещены на уровне БД» — **при добавлении `BEFORE INSERT`-триггера** на уровне **приложения и обычных SQL-клиентов** триггеров достаточно; от того, кто может менять схему или файл, SQLite защитить не может в принципе — для такой угрозы нужны внешняя копия/якорь, а не другая БД (PostgreSQL защищает от этого только раздачей прав: отзыв `DELETE/UPDATE` у роли приложения — при отдельном DBA, которого у проекта нет).

| Рост журнала | > 300 МБ/год (уровень s2+) | `SELECT COUNT(*) FROM transport_journal` × 750 Б |
| Хостинг | переезд на VPS/выделенный сервер с PostgreSQL, или появление второго сервера приложения (несколько хостов пишут в один файл — SQLite не подходит) | решение владельца |
| Требования | сторонняя отчётность/BI напрямую к БД, ролевая защита журнала от админа, репликация | решение владельца |
Промежуточная мера до PostgreSQL (дешевле): вынести `transport_journal` в отдельный файл `data/transport.db` (`ATTACH`) — разгружает файл от `save.php`.

### 6.4 Что сделать уже сейчас, чтобы переезд позже был дешёвым
1. **Один слой доступа:** весь SQL Транспорта — в `api/transport_lib.php` (репозиторные функции), эндпоинты SQL не пишут; соединение берёт только `Database::getInstance()->getPDO()`.
2. **Переносимый SQL:** `ON CONFLICT … DO UPDATE/NOTHING` вместо `INSERT OR IGNORE/REPLACE` (PG-совместимо; убирает и обход журнала), без `datetime()/strftime()/GROUP_CONCAT/IFNULL/GLOB/COLLATE NOCASE/PRAGMA` вне `db.php`; время — строка `YYYY-MM-DDTHH:MM`, как в `00_COMMON.md` (сравнивается одинаково в SQLite и PG); `lastInsertId` — через одну функцию-обёртку.
3. **Схема в ANSI-типах:** `INTEGER/TEXT`, `CHECK`, FK; `AUTOINCREMENT` — только в `schema.sql`; никакого `STRICT`/`WITHOUT ROWID`/рекурсивных CTE (уже в `00_COMMON.md`). Все миграции — добавляющие.
4. **Транзакционная семантика — в одном месте** (`transport_begin_write/commit/rollback`): при переезде меняется тело (`BEGIN` + `SELECT … FOR UPDATE`), а не 18 мест.
5. **Тесты на копии БД через `SC_APP_DB`** сохраняются, но писать их через общий хелпер открытия БД, а не `new PDO('sqlite:…')` в каждом файле (сейчас — 27 файлов, §1.3).
6. **Бэкап-процедура журнала:** якорь последнего `row_hash`/счётчика строк (если владелец примет §5) — переносим и на PostgreSQL.
