# V10 — Модуль «Транспорт». Общие правила для всех задач фазы

Статус: «Старт» на фазу V10-A получен владельцем 2026-11-21. Решения владельца и координатора ниже **обязательны** и пересмотру воркером не подлежат. Неясность — `kanban block` с вопросом, а не догадка. Полный план — `reports/V10/PLAN.md` (принят владельцем), контракт API — `specs/CONTRACT.md`, макеты — `reports/V10/mockups/`. Фоновые материалы (только чтение): каталог `Модуль Транспорт/` в корне репозитория.

## Решения владельца (дословно, 2026-11-21)

1. Права:
   - Admin правит любые заявки. Перемещает ТС между базами.
   - Supervisor_zone0 правит заявки созданные им — смена статусов, назначения, правка.
   - Supervisor_zone1 правит заявки созданные только им — смена статусов, назначения, правка.
   - Viewer не правит никакие заявки. **Перемещает ТС между базами** (владелец подтвердил: это не опечатка).
   - Чужие заявки видны всем ролям.
2. Перенос ТС между базами — постоянное изменение.
3. Список водителей берётся из группы «Транспорт» главной страницы (в dev-БД это группа `g6`, в ней нет сотрудников — фикстуры только синтетические) + сотрудники-совместители, которых админ добавляет в справочник (`transport_driver_pool`). Бригада — любые сотрудники. **Реальные ФИО в репозиторий не попадают** (`AGENTS.md`, `check_no_pii.sh`).
4. Справочник ТС правит только admin. «База» заменяет поле «населённый пункт нахождения». Сущности «зона» в модуле Транспорт нет.
5. Шаг 15 минут: стоянки, время в пути между точками, длительность назначения.
6. Журнал — отдельная таблица `transport_journal` без очистки (7-дневная очистка `audit_log` — `api/helpers.php` `audit_cleanup` — её не касается), правка и удаление записей запрещены (на уровне БД).
7. Карта: OpenStreetMap в форме распределения. Наружу уходят только координаты и названия населённых пунктов. Расстояние и время в пути считаются по карте с округлением вверх до 15 минут и подставляются кнопкой. Прогноз длительности остаётся ручным.
8. У строки точки остановки («+ остановка») есть кнопка «На карте»; по нажатию всплывает модальное окно карты.

## Решения координатора (владелец уведомлён, можно поправить до приёмки)

- SQLite остаётся (PostgreSQL в релизе 1 не вводится); обоснование числами — T3.
- Время хранится как `start_at` + `duration_min` + вычисляемый `end_at`, часовой пояс +05 (наивная локальная строка `YYYY-MM-DDTHH:MM`).
- Предупреждения не блокируют (пересечения ТС/водителя/бригады, отпуск/командировка, ТС в ремонте, расхождение суммы маршрута и прогноза): подтверждаются `confirm_token`.
- «Свой» = `created_by` равен `users.id` текущего пользователя. Исключение — слова владельца о `supervisor_zone0`: он правит также заявки, созданные `supervisor_zone1` (карта `TRANSPORT_EDIT_DELEGATION`, `specs/CONTRACT.md`); `supervisor_zone1` — только свои. Роль — через `user_role()` (`api/auth.php`): `admin` / `supervisor` / `viewer`.
- Перенос ТС — исключение из «viewer только читает»: отдельное действие с проверкой «admin или viewer»; любая другая запись viewer → 403.
- Названия баз («Урай», «Междуреченский»…) в миграцию НЕ зашиваются (написание из голосового не проверено): базы создаёт admin через справочник; в тестах — синтетические.
- Миграция только добавляющая (`CREATE TABLE IF NOT EXISTS`, `ALTER TABLE … ADD COLUMN` под проверкой `PRAGMA table_info`), как v12–v14. Backend совместим с PHP 8.1 (`DEPLOY_HOSTLAND.md`); SQL без возможностей новее SQLite 3.8 (рекурсивные CTE, оконные функции, `RETURNING`, `STRICT` не использовать).

## Правила качества

- Каждое правило/ошибка — сначала тест (красный), потом код, потом зелёный; вывод красного прогона до реализации сохранить в отчёт-файл (в T1 и T2).
- Новые тесты — в **свой новый** файл сьюта и своё имя в `scripts/verify_all.sh` (`BASELINE`, `ALL_SUITES`, `run_suite` — поднять на фактическое число); существующие сьюты не уменьшать. Тесты, зашитые на `schema_version == 14`, обновить осознанно (T1) и перечислить в отчёте.
- Гейт: `bash scripts/verify_all.sh` → `GATE: PASS`, таблица целиком в отчёте. `bash scripts/check_no_pii.sh` → `OK`. `php -l` для изменённых PHP-файлов.
- `AGENTS.md` не редактировать: нужные правки — файлом `reports/V10/<task>_AGENTS_patch.md` («было/стало»), координатор применит.
- Коммит: в сообщении id своей Kanban-задачи (хук `commit-msg`, сьют `tasklink`). Хук не обходить. После тестов `git checkout -- data/app.db`; `git status --porcelain` — только файлы задачи. Коммитить в **своей ветке своего worktree**; в main и в чужие worktree не писать; не пушить.
- Внешних эффектов нет: никакого деплоя, push, Telegram, вызовов n8n/HelpMe, записи в `data/app.db` (миграции — на КОПИИ). Исключение — только публичные запросы T4, описанные в его спеке.
- При ошибке провайдера (429/402/400 context) — `kanban block`, **не** `complete`.
- Тесты и отчёты: данные синтетические; реальных ФИО нет.
- Утверждения о коде — с `file:line`, прочитанными на текущем коммите. Приёмка — по `git diff`, `verify_all.sh` и тестам, не по индексу.
- Отчёт: `reports/V10/<TASK>_REPORT.md` (T3/T4 — свои названия): что сделано (file:line), чем проверено, GATE-таблица, риски, открытые вопросы.
