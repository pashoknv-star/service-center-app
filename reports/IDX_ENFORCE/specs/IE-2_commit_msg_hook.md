# IE-2 — хук `commit-msg`: коммит с кодом только с id Kanban-задачи

Role: implementer (repo tooling). Delivery owner: software-development-coordinator. Return: Kanban-квитанция + отчёт в репозитории.
Решение владельца 2026-11-16: код меняется только через Kanban-задачу; способ принуждения — хук `commit-msg`.
Зависимость: IE-1 (тот же `scripts/verify_all.sh`, работа строго после него).

## Objective

Коммит, меняющий код проекта, отклоняется, если в его сообщении нет id существующей Kanban-задачи. Обход через `git commit --no-verify` обнаруживается gate.

## Контекст (проверено координатором на коммите 56fecf8)

- В репозитории нет активных хуков: в `.git/hooks` только `*.sample`, `core.hooksPath` не задан.
- Kanban хранится в SQLite `/home/hermes/.hermes/kanban.db`, таблица `tasks`, столбец `id` вида `t_941ab009` (`t_` + 8 hex).
- Фаза V7 (коммиты `b27734b`…`3826b2e`) прошла без Kanban-задач — это случай, который хук должен исключить.
- `main` опережает `origin/main` только коммитами с файлами `reports/` (документы).

## Scope

Создать:
- `scripts/hooks/commit-msg` (bash, исполняемый, под контролем версий);
- `scripts/check_commit_tasks.sh` — проверка диапазона коммитов;
- `scripts/test_commit_msg_hook.sh` — самотесты;
- `reports/IDX_ENFORCE/IE-2_REPORT.md`.

Изменить: `scripts/verify_all.sh` (новый сьют `tasklink`, `BASELINE[tasklink]`), `AGENTS.md` (новый подраздел в «Repository rules» + строка в таблице сьютов + эталон), `PROGRESS.md`.

Выполнить в основном репозитории: `git config core.hooksPath scripts/hooks`.

Out of scope: продакшен-код (`index.html`, `js/`, `api/`), `data/app.db`, сьют `refs` и его файлы (IE-1), переписывание истории, push, деплой, правки вне репозитория.

## Требуемое поведение

1. **Какие коммиты проверяются.** Коммит «с кодом» — в нём изменён хотя бы один путь вне списка документов. Документы: `reports/**`, `staff_project/**`, любые `*.md`. Всё остальное (`index.html`, `js/`, `api/`, `scripts/`, `n8n/`, `data/`, `static/`, `router.php`, `.htaccess`, конфиги) — код.
2. **Правило.** В сообщении коммита с кодом есть хотя бы один id вида `t_[0-9a-f]{8}`, и хотя бы один из них существует в Kanban. Коммит только с документами проходит без id.
3. **Проверка существования.** Путь к БД — переменная `KANBAN_DB`, по умолчанию `$HOME/.hermes/kanban.db`; чтение только `sqlite3 -readonly`. БД или `sqlite3` недоступны — проверяется только формат, в stderr предупреждение (коммит не блокируется из-за недоступной инфраструктуры).
4. **Merge-коммиты** (есть `MERGE_HEAD`) проходят без id: id несут вливаемые коммиты.
5. **Сообщение об отказе** на русском: причина, список файлов кода в коммите, пример правильного сообщения. Упомянуть, что `--no-verify` агентам запрещён.
6. **`scripts/check_commit_tasks.sh [<range>]`** — то же правило для каждого не-merge коммита диапазона (по умолчанию `origin/main..HEAD`): печатает нарушителей (`sha`, тема, файлы кода), exit 1 при нарушениях. Пустой диапазон — PASS.
7. **Сьют `tasklink`** в `verify_all.sh`: FAIL, если `git config core.hooksPath` ≠ `scripts/hooks`, хук отсутствует или не исполняемый, самотесты не прошли, либо `check_commit_tasks.sh` нашёл нарушения в `origin/main..HEAD`. `CNT` = число пройденных самотестов.
8. **AGENTS.md:** правило «коммит с кодом — только с id Kanban-задачи»; команда включения хука на свежем клоне; запрет `--no-verify` для агентов; что делать, если задачи нет (сначала создать задачу через координатора).

## Acceptance Criteria

Самотесты работают во временном репозитории в `$TMPDIR` с фикстурой Kanban-БД (через `KANBAN_DB`), основной репозиторий и настоящий Kanban не трогают, за собой убирают. Обязательные случаи:

1. Изменён `js/x.js`, в сообщении нет id → отказ, exit ≠ 0.
2. Изменён `js/x.js`, id правильного формата, но такой задачи нет в БД → отказ.
3. Изменён `js/x.js`, id существует → коммит создан.
4. Изменён только `reports/x.md`, id нет → коммит создан.
5. Изменены `api/x.php` и `reports/x.md`, id нет → отказ.
6. Merge-коммит без id → создан.
7. `KANBAN_DB` указывает на несуществующий файл, id правильного формата → коммит создан, в stderr предупреждение; без id → отказ.
8. Строка-комментарий `# t_12345678` в шаблоне сообщения id не считается.
9. `check_commit_tasks.sh` на диапазоне с одним коммитом кода без id (создан с `--no-verify`) → exit 1 и sha нарушителя; на диапазоне без нарушений → exit 0.
10. Коммит из связанного worktree (`git worktree add`) проходит ту же проверку (хук действует и там).

Плюс:
11. В основном репозитории `git config core.hooksPath` выводит `scripts/hooks`; твои собственные коммиты этой задачи созданы уже через хук и содержат её id.
12. `bash scripts/verify_all.sh` на итоговом коммите → `GATE: PASS`, сьюты `refs` и `tasklink` в таблице, `clean PASS`.
13. `git status --porcelain` пуст; в диффе нет продакшен-файлов.
14. В отчёте описано поведение при `git commit --amend`, `git revert`, `git cherry-pick` и `git rebase` (проверено запуском, с выводом): вызывается ли хук и что требуется от автора.
