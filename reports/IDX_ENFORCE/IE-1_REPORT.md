### Как проверка работает

1. **База.** `VERIFY_BASE` задан, но не существует → FAIL. Не задан: нет `origin/main` → PASS «удалённых функций: 0»; есть — `merge-base HEAD origin/main` (нет merge-base → FAIL). Если база совпадает с текущим деревом — просто 0 удалённых (сравнение выполняется всё равно, поэтому незакоммиченные удаления при `база = HEAD` тоже ловятся).
2. **Определения** (только продакшен-файлы: `index.html`, `js/*.js` кроме `js/test_*`, `api/*.php` кроме `*_test.php`, корневые `*.php`; строки-комментарии не считаются): `function name(` (JS/PHP, методы, `async`, `function*`, `function &name(`), `name: function`, `name = function` (в т.ч. `X.name = function`), `name = (..) =>` / `name: (..) =>` / `name = x =>` и с `async` (в т.ч. `const|let|var`), shorthand-методы `name(args) {` (только JS-подобные файлы; с исключением ключевых слов). Имя «удалено», если в базе определено где-то в этих файлах, а в текущем дереве — нигде (в т.ч. файл удалён целиком).
3. **Ссылки:** целое слово (`(?<![\w$])имя(?![\w$])`) в каждой строке каждого текстового файла дерева (не бинарный, ≤ 5 МБ), кроме `reports/`, `staff_project/`, `*.md`, `CODEMAP.md` и трёх файлов самого инструмента (`check_removed_refs.js`, `test_removed_refs.js`, `removed_refs_allow.txt` — они называют имена в данных; без этого самотест случая 3 падал бы на собственном тексте). Не считаются: строки целиком `//`, `#` (php/sh/py/yml/txt…), `--` (sql), блоки `/* */` (в т.ч. многострочные), `<!-- -->` (html/php).
4. **Исключения:** `имя  # причина`; пустая причина / неверный формат → FAIL; `K` в `NOTE` = число записей в файле (видно всегда), применённые исключения и неиспользуемые записи печатаются отдельными строками.
5. Сообщения на русском; FAIL содержит «Что делать: обновите оставшиеся ссылки … или внесите имя в scripts/removed_refs_allow.txt строкой «имя  # причина»».

## 4. Ограничения проверки (чего она НЕ ловит / где шумит)

**Определения, которые не распознаются** (удаление такой функции не будет замечено):
1. Многострочные параметры стрелки: `const f = (a,\n b) => …`; стрелки с вложенными скобками в параметрах (`(a = fn()) =>`, `([x, y]) =>` ловится, `({a}) =>` ловится, `(a = (1)) =>` — нет).
2. Shorthand-методы с `{` не в конце строки (`foo() { return 1; }`) и с многострочными параметрами; в PHP shorthand не применяется (там всегда `function`).
3. Динамические определения: `window[name] = …`, `Object.defineProperty`, `obj['name'] = function`, `exports = {name}` без `function`, переменные-функции через `bind`/`compose`, сгенерированный код, `eval`.
4. Определения в HTML-атрибутах / строках внутри шаблонов (`<script>` в строковом литерале).
5. Определения вне перечисленных файлов (`n8n/code/*.js`, `scripts/*.js`, `js/test_*`) — намеренно не относятся к продакшену по ТЗ.
6. Имя, определённое в нескольких местах: если удалена одна из одноимённых функций (например `render`, `save`, `get`), а другая осталась — удаление **не** замечается (критерий ТЗ: «определения нет нигде»). Перенос функции между файлами корректно не считается удалением.
7. Изменение сигнатуры/семантики без смены имени (не в задаче).

**Ссылки, которые не распознаются / ложные:**
8. Ссылка по склеенному/вычисляемому имени (`window['mask' + 'PhoneField']`, префикс + имя, `on${name}`), ссылка через префикс/регэксп, имена в JSON-строках разделённые («`mask`, `PhoneField`»).
9. Ссылки в `reports/`, `staff_project/`, `*.md`, `CODEMAP.md`, а также в трёх файлах инструмента — не проверяются (по ТЗ).
10. Бинарные и > 5 МБ файлы не читаются.
11. Хвостовые комментарии (`код; // имя`) НЕ вырезаются — имя в них считается ссылкой (строже). Строки целиком — комментарий определяются эвристикой по началу строки: комментарий-маркер внутри строкового литерала/регэкспа на «начале строки» (например, строка шаблона, начинающаяся с `//`) будет принят за комментарий (редкий пропуск); `#` в `.php` считается комментарием, в `.js`/`.html` — нет.
12. **Шум (ложные FAIL):** слово ищется везде как целое слово, поэтому общие имена (`act`, `id`, `status`, `load`) при удалении определения «находятся» в несвязанном тексте (атрибуты `data-tk-act`, поля JSON, SQL, ключи). Пример на реальной истории: `VERIFY_BASE=HEAD~20` → имена `act`, `calCopyPayload`, `id`, `act` — 319 вхождений; это дорожка для `removed_refs_allow.txt` (с причиной) либо уточнения. Настоящее срабатывание на той же истории: `VERIFY_BASE=HEAD~60` → `reassignTask`: 5 ссылок в `scripts/test_tasks_frontend.js` и `scripts/v6*_accept*.js` (устаревшие тесты, ссылаются на `data-tk-act="reassignTask"`).
13. Закомментированная строка, содержавшая определение, определением не считается (удаление «комментированием» ловится как удаление, если остались ссылки).
14. Продакшен-файлы без расширения/в подкаталогах (`api/sub/*.php`, `js/vendor/*.js`) определениями не считаются; ссылки в них ищутся.
15. Сравнение — по именам, не по смыслу: две «разных» функции с одним именем неразличимы.

6. **Трактовка «исключений K»:** `K` = число записей в allow-файле (видно всегда); `M` = все удалённые имена, на которые остались ссылки (включая закрытые исключением); FAIL, если среди `M` есть имя без исключения. Применённые исключения и неиспользуемые записи печатаются построчно.
7. **Нет базы** (`origin/main` отсутствует и `VERIFY_BASE` не задан) → PASS с пометкой, по ТЗ; следствие: в клоне/CI без `origin/main` проверка тихо пропускается — задавать `VERIFY_BASE`. Текущий локальный `main` опережает `origin/main` (`0b8aa69`), на момент сдачи база = `0b8aa69`; после push координатором база станет `HEAD` и проверяться будут только незакоммиченные правки (для проверки коммита — `VERIFY_BASE=<родитель>`; это зона IE-2).
8. В тестовых вариантах «удаление определения» функция вырезается по балансу `{}` (`removeDef` в самотесте); для случая 2 проверено, что вырезана только `migrate` (`removed=1`).
