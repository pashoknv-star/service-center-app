# Роль
Ты — ведущий инженер по безопасности приложений и senior full-stack ревьюер (PHP + SQLite + vanilla JS) с опытом пентеста веб-приложений. Проведи глубокий аудит кода приложения **service-center-app** («Сервисный центр Урай и Кондинский район»): безопасность, защита персональных данных, корректность, надёжность, производительность, сопровождаемость. Работай одновременно как враждебный атакующий (в том числе злонамеренный сотрудник с ролью viewer или supervisor) и как придирчивый техлид. Цель — найти реальные дефекты, а не подтвердить, что всё хорошо.

**Режим: ревью + план, ничего не правь.** Код, БД, конфиги, git-историю и прод не изменяй. Исправления предлагай в отчёте в виде патчей.

# Контекст проекта
- **Назначение:** внутренний веб-инструмент сервисного центра: справочник сотрудников (карточки с фото), матрица отпусков/больничных/отгулов на год, производственный календарь РФ, сущность «Командировки» (прогноз → подтверждение) с передачей заявок RPA-роботу в HelpMe, журнал аудита. Публичной части нет: всё за логином, круг пользователей — сотрудники СЦ.
- **Стек:** PHP (без фреймворка) + SQLite через PDO (WAL, foreign_keys=ON, busy_timeout) + vanilla JS без сборки. Фронтенд — монолит `index.html` (~1,1 МБ, inline JS/CSS), а также `js/storage.js` (StorageAdapter) и `js/trips.js`. Backend — `api/*.php`, схема — `api/schema.sql` (v8), инкрементальные миграции в `api/db.php` применяются первым HTTP-запросом. Обработка фото — GD/Imagick (обрезка 512×512, WebP, удаление EXIF).
- **Окружение:**
  - локально: PHP 8.3, `php -S 127.0.0.1:8090 router.php`, dev-БД `data/app.db` лежит в git;
  - прод: Hostland, shared-хостинг, AlmaLinux 8.10, nginx-прокси → Apache (mod_php, **PHP 8.1**), CLI PHP 5.3, без sudo, без Docker. **HTTP без TLS** (риск принят владельцем). Корневой `.htaccess` с `php_flag` на прод не выкладывается (даёт 500); `data/.htaccess` — `Require all denied`; `images/.htaccess` — запрет исполнения PHP. Бэкапы — `sqlite3 .backup` через планировщик панели Hostland. Состав прод-пакета и порядок выкладки — `DEPLOY_HOSTLAND.md`.
- **Персональные данные** (152-ФЗ): ФИО, телефоны, фото, должность, подразделение, населённый пункт; периоды отпусков, отгулов и **больничных** (`sick` / ЭЛН — потенциально сведения о состоянии здоровья, специальная категория); командировки: маршрут (`origin`, `location`), гостиница, вид транспорта, **сумма аванса**, телефон, бизнес-процесс. ПДн передаются третьим лицам/системам: RPA-роботу HelpMe (payload в `trip_requests`) и выгружаются через экспорт/аудит.
- **Учётные данные и секреты:** пароли пользователей (`password_hash`), PHP-сессии (cookie `PHPSESSID`, HttpOnly, SameSite=Lax, `secure=false`), токен внешнего импорта `meta.external_api_token` (Bearer), токен робота `meta.rpa_relay_token` (заголовок `X-Auth-Token`, создаётся лениво, раскрывается через `trip_relay.php?action=reveal`).
- **Роли и акторы:**
  - аноним;
  - `viewer` — только чтение;
  - `supervisor` — пишет только `trip`/`day_off` и командировки в своей зоне (`scope_group_id`), записи `approved`/`confirmed` — только чтение;
  - `admin` — всё, включая правку `approved`/`confirmed`, импорт/восстановление и экспорт аудита;
  - машинные акторы: внешняя система импорта отпусков (Bearer → `api/vacation_import.php`), RPA-робот HelpMe (`X-Auth-Token` → `api/trip_relay.php`: poll/callback).
  - **Проектное решение (E8-4):** видимость глобальная — все роли видят всех сотрудников и все записи; зона ограничивает только запись. Сама по себе глобальная видимость дефектом/IDOR не является, но её последствия для ПДн оцени отдельно.
- **Особо важные зоны:**
  - аутентификация и сессии: `api/login.php`, `logout.php`, `session.php`, `change_password.php`, `auth.php`;
  - авторизация по ролям и зонам, approved/confirmed-guard: `save.php`, `entries.php`, `trips.php`, `employees.php`, `groups.php`, `positions.php`, `holidays.php`;
  - массовые операции и защита данных от «устаревших вкладок» (инциденты E10: массовое стирание фото и календаря; guard'ы и freshness-протокол в `save.php`/`sync.php`/`js/storage.js`);
  - полное восстановление и экспорт: `import.php` (удаляет и перезаливает данные), `export.php` (доступен любому залогиненному, включая viewer), `reset.php`, `load.php`, `audit_export.php`;
  - машинные интерфейсы: `vacation_import.php` (поиск сотрудника по id/ФИО), `trip_relay.php` (очередь, токен, reveal);
  - загрузка фото: `api/upload.php`, корневой `upload.php`, каталог `images/`;
  - диагностические/служебные файлы: `api/debug_token.php`, `api/init_db.php`, `api/seed_positions.php`, `api/smoke_test.php`, `test_*.php`/`test_*.sh` в корне — проверь, какие из них попадают в прод-пакет и что доступно по вебу;
  - CORS и общие заголовки: `api/helpers.php`; `router.php`; все `.htaccess`.

# Чек-лист

## A. Безопасность (OWASP Top 10 применительно к PHP + SQLite + vanilla JS)
- **SQL-инъекции:** все запросы PDO — только prepared statements? Динамические фрагменты (имена полей, сортировка, `IN (...)`), `$pdo->exec()` с данными, строки миграций.
- **XSS:** хранимый (ФИО, должность, комментарии, названия/места/гостиница командировок, названия групп, данные из `vacation_import.php` и `import.php`, `last_error` из callback робота), отражённый, DOM-based. Все места `innerHTML`/`insertAdjacentHTML`/шаблонных строк в `index.html` и `js/*.js`; экранирование при выгрузке аудита в CSV/MD/XLSX (в том числе CSV/формульная инъекция `=`, `+`, `-`, `@` для Excel).
- **Аутентификация:** хранение паролей (`password_hash`/`password_verify`), минимальная длина и сложность, отсутствие защиты от перебора и rate limiting на `login.php`, перечисление пользователей по ответам/таймингу, стартовые пароли `changeme` (могут ли попасть на прод через `init_db.php`), смена пароля (требование текущего пароля, инвалидация других сессий).
- **Сессии и токены:** флаги cookie (HttpOnly, SameSite, Secure — с учётом HTTP), `session_regenerate_id` при логине (фиксация сессии), срок жизни, инвалидация при выходе и смене пароля. Токены `external_api_token` и `rpa_relay_token`: энтропия генерации, сравнение за постоянное время (`hash_equals`), хранение в открытом виде, ротация, кто может раскрыть (`reveal` доступен supervisor?), утечка в ответах, логах, `debug_token.php`, git-истории `data/app.db`.
- **Авторизация:** для каждого изменяющего эндпоинта проверь серверную проверку роли и зоны (supervisor вне своей `scope_group_id`, supervisor на типах кроме `trip`/`day_off`, правка `approved`/`confirmed` не-admin'ом, viewer на POST/PUT/DELETE), mass assignment (поля `version`, `approvalStatus`, `status`, `created_by`, `scope_group_id`, `isAdmin` в теле), обход через `save.php` (полный upsert) в обход точечных эндпоинтов, проверки только на фронтенде, эскалацию до admin.
- **CSRF:** все изменяющие запросы. Достаточно ли SameSite=Lax с учётом `Access-Control-Allow-Origin: *`, обработки `OPTIONS`, приёма form-urlencoded/`text/plain` вместо JSON, GET-запросов с побочными эффектами (`reset.php`, `reveal`, ленивое создание токена).
- **CORS:** `corsHeaders()` в `api/helpers.php` — wildcard, разрешённые методы и заголовки; реальный риск с cookie-сессией и с токенными эндпоинтами.
- **Path traversal / LFI:** параметр `year` в `holidays_provider.php`, имена файлов при загрузке и удалении фото, `photo_url` из тела запроса, временные файлы экспорта, `router.php` (`urldecode` + `file_exists`).
- **Загрузка файлов:** проверка типа по содержимому (fileinfo/getimagesize), размер, пиксельные бомбы (декомпрессия в GD/Imagick), имя файла, место хранения, возможность исполнения в `images/` на Apache (и при отсутствии `.htaccess`), SVG/HTML, удаление EXIF; корневой `upload.php`-делегат.
- **Секреты и служебные файлы:** токены и пароли в коде, `data/app.db` в git (хеши, токены, ПДн в истории), доступность по вебу `data/app.db`, `app.db-wal`/`-shm`, `.git/`, `*.md`, `docs/API_DOCUMENTATION.json`, `api/schema.sql`, `api/smoke_test.php`, `api/init_db.php`, `api/debug_token.php`, корневых `test_*.php`.
- **HTTP-заголовки:** CSP, X-Content-Type-Options, X-Frame-Options/frame-ancestors, Referrer-Policy, Cache-Control для ответов с ПДн (`load.php`, `export.php`, `sync.php`). HSTS неприменим, пока нет TLS. Проверь и по коду, и анонимными GET/HEAD к проду.
- **Отсутствие TLS** (риск принят владельцем): оформи как находку с пометкой «риск принят владельцем» и оцени текущие последствия — перехват паролей при логине и смене пароля, перехват сессии, ПДн в ответах API, токены импорта и relay в заголовках, MITM-подмена JS.
- **Утечки информации:** stack trace и пути в ответах API (`catch` с `$e->getMessage()`), `display_errors` на проде (корневой `.htaccess` не выкладывается), листинг каталогов, подробные сообщения об ошибках для анонима.
- **Бизнес-логика:**
  - обход approved/confirmed-guard и зоны через альтернативные эндпоинты (`save.php`, `entries.php`, `import.php`, `vacation_import.php`);
  - пересечения командировок с отпуском/отгулом (409), даты `end < start`, отрицательный или чрезмерный `advance_amount`, недопустимые `transport_*_mode`/`business_process`;
  - конфликт версий (`version`/`entryVersion`) — тихая перезапись чужих изменений;
  - защита от массового стирания устаревшим клиентом (фото, календарь, sync-delete) — обходится ли она;
  - `vacation_import.php`: неоднозначный поиск по ФИО (однофамильцы), запись не тому сотруднику, повторная доставка;
  - `trip_relay.php`: повторная выдача заявки, подделка или повтор callback, гонки claim/callback, бесконечные `attempts`, ручная правка командировки после постановки в очередь (payload заморожен);
  - `import.php`: полное удаление данных при частично невалидном backup;
  - race conditions (TOCTOU) при параллельной работе двух вкладок или пользователей.
- **Персональные данные (152-ФЗ, технические меры):**
  - минимизация: какие ПДн реально нужны каждой роли, полный дамп ПДн для viewer через `export.php`/`load.php`;
  - ПДн и сведения о больничных в `audit_log`, `sync_log`, `trip_requests.payload`, `last_error`, серверных логах;
  - сроки хранения: аудит — 7 дней, `sync_log`, `trip_requests`, бэкапы на хостинге — 30 копий, фото уволенных/удалённых сотрудников;
  - передача третьим лицам: какие поля уходят в HelpMe и внешней системе импорта, нет ли лишних;
  - удаление сотрудника: каскад и «осиротевшие» фото в `images/`;
  - защита бэкапов и экспортов (в открытом виде, где лежат).
  - Юридические вопросы (основания обработки, согласия, специальная категория «здоровье», уведомление Роскомнадзора, локализация, договор с HelpMe) не оценивай по существу — перечисли и пометь «требует проверки юристом».
- **Защитный пункт:** если найдёшь в коде XML-парсинг, `unserialize`, вызовы shell, `eval`, исходящие HTTP-запросы, редиректы по пользовательскому вводу или `include`/`require` с переменной — проверь их по соответствующим классам OWASP (XXE, десериализация, command injection, SSRF, open redirect, RFI). На момент составления промпта таких мест не было (кроме генерации XLSX через ZipArchive и чтения локальных JSON).

## B. Корректность и надёжность
- Логические ошибки и граничные случаи: пустые/null/очень большие значения, Unicode в ФИО (ё/е, пробелы, регистр — важно для поиска по ФИО), даты `YYYY-MM-DD`, високосные годы, переход года, часовые пояса (сервер в UTC через `date('c')` против локального времени UTC+5 в браузере), производственный календарь вне 2026–2028.
- **Совместимость PHP:** код разрабатывается на 8.3, а прод — 8.1. Найди конструкции, которых нет в 8.1 (readonly-классы, типизированные константы, `json_validate`, DNF-типы и т.п.). CLI-скрипты на хостинге не запускаются (PHP 5.3).
- Обработка ошибок: проглоченные исключения, неконсистентное состояние после сбоя, операции без транзакции (особенно в `import.php`, `save.php`, `trips.php`, `trip_relay.php`), неверные HTTP-коды.
- Конкурентность SQLite: `SQLITE_BUSY` при WAL и `busy_timeout`, длинные транзакции полного `save.php`, идемпотентность повторов (relay, импорт, двойной клик).
- Валидация входных данных на сервере для каждого поля (фронтенд-валидация не считается).
- Миграции при первом HTTP-запросе: гонка двух параллельных запросов, частично применённая миграция, идемпотентность DDL.
- Фронтенд: синхронизация (polling `sync.php`, focus), `lastSyncId`, поведение при обрыве сети и истёкшей сессии (401 посреди редактирования), потеря несохранённых изменений.

## C. База данных (SQLite)
- N+1-запросы, отсутствующие индексы под реальные выборки (`schedule_entries` по году/сотруднику, `sync_log` по id, `trip_participants`), `SELECT *`, неограниченные выборки без пагинации (`entries.php` без параметров, `load.php`, `export.php`).
- Схема: целостность внешних ключей (включён ли `foreign_keys` на каждом соединении), CHECK-ограничения на статусы, рассинхрон `schema.sql`, миграций в `db.php` и кода, `SCHEMA_VERSION`.
- Рост таблиц `sync_log`, `audit_log`, `trip_requests`: очистка, размер БД, `VACUUM`.
- Файл БД: права, недоступность по вебу (включая `-wal`/`-shm`), корректность бэкапа через `sqlite3 .backup` при WAL, ни один код-путь не перезаписывает/не пересоздаёт прод-БД.

## D. Производительность

# Требования к находкам
Для КАЖДОЙ находки укажи:
- **ID** и **заголовок**
- **Приоритет**: P0 / P1 / P2 / P3 (P0 — немедленно: эксплуатируемая уязвимость, утечка ПДн или потеря данных на проде; P1 — высокий; P2 — средний; P3 — низкий / улучшение). Для уязвимостей дополнительно укажи справочную оценку CVSS 3.1 (вектор + балл).
- **Категория** (A–G) и, если применимо, CWE/OWASP
- **Место**: `файл:строка` (или диапазон) — обязательно
- **Доказательство**: минимальный фрагмент кода (секреты и ПДн маскировать)
- **Сценарий эксплуатации или сбоя**: конкретные шаги, роль атакующего (аноним / viewer / supervisor чужой зоны / владелец токена) и пример запроса/payload. Воспроизводить — только на локальном dev.
- **Последствия** для сервисного центра, сотрудников и их ПДн
- **Исправление**: конкретный патч или код (совместимый с PHP 8.1 и Hostland, без `php_flag`), а не общий совет. Не применять.
- **Уверенность**: подтверждено (по коду / на локальном dev / анонимным запросом к проду) / вероятно / требует проверки (с объяснением, чего не хватает)
- **Статус риска**: при необходимости — «риск принят владельцем» (например, отсутствие TLS) или «проектное решение» (например, глобальная видимость)

# Правила
- Не выдумывай: каждая находка должна опираться на реально прочитанный код или реально полученный ответ сервера. Если файл не просмотрен, так и скажи.
- Не ограничивайся первыми найденными проблемами — пройди весь чек-лист. Если категория чиста, явно напиши «проверено, проблем не найдено» и что именно проверено.
- Не снижай приоритет из вежливости. Не раздувай его ради объёма.
- Не выдавай задокументированное проектное решение (глобальная видимость, HTTP без TLS) за неизвестный дефект: помечай статус, но последствия оценивай честно.
- Без общих фраз вроде «следуйте лучшим практикам» — только конкретика.
- Ничего не изменяй в репозитории и на проде. Если dev-БД изменилась при проверке — верни её (`git checkout -- data/app.db`).

# Формат итогового отчёта
1. **Резюме** (5–10 строк): общее состояние, главные риски для ПДн и данных, допустима ли дальнейшая эксплуатация в текущем виде и что нужно исправить немедленно.
2. **Карта системы и поверхность атаки** (кратко), включая перечень эндпоинтов и файлов, доступных на проде.
3. **Таблица находок**: ID | Приоритет | CVSS | Категория | Место | Заголовок | Статус риска — отсортировано по приоритету.
4. **Детальное описание находок** в формате выше.
5. **Что проверено и признано корректным.**
6. **Принятые риски и проектные решения** — с текущей оценкой последствий.
7. **Вопросы для юриста по 152-ФЗ** (перечень, без оценки по существу).
8. **Что не удалось проверить** (нет доступа, нет файлов, требуется авторизованная проверка на проде, сторона HelpMe или внешней системы импорта).
9. **План исправлений**: немедленно (P0), следующая фаза (P1), технический долг (P2–P3). Учитывай, что деплой выполняется только по команде владельца «Деплой».
