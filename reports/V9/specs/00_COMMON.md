# V9 — Блок «Задачи»: связанные задачи. Общие правила для всех задач фазы

Статус: «Старт» получен владельцем 2026-11-18. Решения владельца и координатора ниже **обязательны** и пересмотру воркером не подлежат. Неясность — `kanban block` с вопросом, не догадка.

## Решения владельца (дословно, 2026-11-18)

1. Задача 2 «рождается» вне зависимости от закрытия задачи 1; это независимые действия. Никаких кнопок «создать из закрытия» не требуется. Закрытие/переоткрытие задачи связей не создаёт и не меняет.
2. Тип связи один, **симметричный** («Связанные задачи»), без ролей «родитель/потомок». Из задачи 2 выбрана задача 1 → в обеих карточках они видны как связанные.
3. Ничего не копировать из задачи 1 в задачу 2 (связь создаётся вручную, копирования полей нет).
4. Реализация — **вариант А**: в карточке задачи (форма), **под блоком «Вложения»**, поле «Связанные задачи» — обычный текст (textarea, свободный текст со ссылками внутри, как в Obsidian). Ключ вызова — **`(())`** (две открывающие и две закрывающие скобки подряд). Когда курсор встаёт **между скобками** `((|))` — открывается модальное окно со списком **всех задач (открытых и закрытых)**; в списке работает поиск (по аналогии со списком исполнителей). После выбора `(())` превращается в токен-ссылку на задачу.
5. Ссылки показываются в карточке задачи **под «Описанием»**, в блоке «Доска» (карточка задачи, открытая с Доски/Списка/Календаря — это одна и та же панель деталей `js/tasks.js` ~1842), как активные ссылки. Клик по ссылке — переход в «Список», где отображаются **все связанные между собой задачи** (вся цепочка/граф целиком: все задачи, достижимые по связям в обе стороны, 1→2→3 — из любой показать все три). **Текущая задача (из карточки которой кликнули) — без выделения и всегда первой строкой.**
6. Если задача удалена (`archived=1`) — ссылка на неё **перечёркивается** у обеих сторон (симметрично).
7. Пишет только admin (как весь блок «Задачи»); supervisor/viewer — только читают (`api/tasks.php:29` — чтение разрешено всем ролям, запись admin). Поэтому «скрывать названия по ролям» не нужно: все роли видят все задачи.

## Решения координатора (владелец уведомлён, можно поправить до приёмки)

- Токен в тексте: `((ID|название))`. Название — только снимок для читаемости в режиме правки (из названия вычищаются `( ) |` и переводы строк, ≤80 симв.); истина — ID, в режиме чтения название берётся актуальное с сервера. Парсится только по ID. Пустое `(())` сервер игнорирует. Допустимые символы ID определить по реальному генератору id задач в `api/tasks.php` на текущем коммите (не угадывать).
- Колонка `tasks.links_text TEXT` (общий лимит длины — как у описания, константа рядом с `TASKS_DESC_MAX`) + таблица `task_links(task_a, task_b, created_at, created_by)`, PK `(task_a, task_b)`, `CHECK (task_a < task_b)` (симметрия — каноническая пара), FK на `tasks(id)` `ON DELETE CASCADE` (жёсткого удаления задач нет, FK — для целостности), индексы по `task_b`. Схема **v14**, только добавление (`IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN` под проверкой `PRAGMA table_info`), как v12/v13.
- Источник истины связей — токены в `links_text` ИСХОДЯЩЕЙ задачи; сервер при `POST`/`PUT` пересобирает строки `task_links` этой задачи в одной транзакции с сохранением самой задачи (общий `version`, 409 `VERSION_CONFLICT` как у остальных полей). Удалил токен у задачи 2 → связь исчезла с обеих сторон. Входящие связи (задача 1 «видит» задачу 2) строятся из таблицы и показываются без правки текста задачи 1.
- Правила: самосвязь запрещена (`link_self`, 422); неизвестный ID в токене — 422 `link_unknown`; новая связь на архивную задачу — 409 `link_target_archived`; уже существующая связь с позже удалённой задачей сохраняется и рисуется перечёркнутой; дубли схлопываются; ≤ 50 различных связей на задачу (`links_too_many`, 422).
- «Задача удалена» = `archived=1` (мягкое удаление, `api/tasks.php` ~1302). Строки `task_links` остаются. Обход графа **не проходит через архивные задачи**; архивные в список «связанных» не попадают.
- Компонент связности — на сервере в PHP (BFS, лимит 200 задач, без рекурсивных CTE: версия SQLite на Hostland не проверена).
- Нужен список всех задач для окна выбора — не из диапазонного `GET ?from&to`: отдельный облегчённый запрос `GET api/tasks.php?pick=1` → `[{id,title,status,start_at}]` всех неархивных (лимит 2000), доступен всем ролям с чтением.
- Бэкенд обязан изменять `updated_at` второй стороны связи (НЕ `version`), если sync клиентов определяет изменения по нему; воркер T1 сначала читает, как работает sync (T1-11 в `js/tasks.js`, поле `dirty`), и фиксирует в отчёте, что именно нужно, чтобы связь появилась в карточке задачи 1 без перезагрузки страницы.
- Фильтр Списка `rel=<id>` (в `S.filters`, `js/tasks.js` ~2312): показывает компонент связности; другие фильтры при `rel` не применяются; в панели фильтров — плашка «Связанные задачи: <название>» с кнопкой «×» сброса. Первая строка — исходная задача (без выделения), остальные — как обычная сортировка Списка.
- Клик по перечёркнутой ссылке — без перехода (подсказка «Задача удалена»).
- Окно выбора: поиск без учёта регистра по названию; исключена сама задача; показывает статус «Открыта/Закрыта»; закрытие — Esc / «Отмена» / клик вне окна; при отмене `(())` остаётся в тексте как есть и повторно окно не открывается, пока курсор не покинет скобки и не вернётся.
- Вывод всех данных — через `esc()`; ссылки — `data-tk-act` + делегирование, как остальной модуль (без inline-onclick; если без него нельзя — экспорт в `window.Tasks`).

## Правила качества

- Каждое правило/ошибка — сначала тест (красный), потом код, потом зелёный; в отчёте — вывод красного прогона до исправления.
- Новые тесты — в **свой новый** файл сьюта и своё имя сьюта в `scripts/verify_all.sh` (BASELINE поднять на фактическое число); существующие сьюты не уменьшать. Тесты, зашитые на `schema_version == 13`, обновить осознанно и перечислить в отчёте.
- Гейт: `bash scripts/verify_all.sh` → `GATE: PASS`, таблица целиком в отчёте.
- `AGENTS.md` не редактировать: нужные правки — файлом `reports/V9/<task>_AGENTS_patch.md` («было/стало»), координатор применит.
- Коммит: в сообщении id своей Kanban-задачи (хук `commit-msg`, сьют `tasklink`). После тестов `git checkout -- data/app.db`; `git status --porcelain` — только файлы задачи.
- Внешних эффектов нет: никакого деплоя, push, Telegram клиентам, вызовов n8n/HelpMe на проде. Миграция проверяется на КОПИИ `data/app.db`.
- При ошибке провайдера (429/402/400 context) — `kanban block`, **не** `complete`.
- Совместимость с хостингом: PHP-синтаксис не новее используемого в `api/tasks.php`; SQL без возможностей новее SQLite 3.8.
