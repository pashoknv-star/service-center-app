#   
Предложение реализации матрицы распределения транспорта по заявкам

[https://github.com/pashoknv-star/service-center-app](https://github.com/pashoknv-star/service-center-app) - для этого репозитория предложи реализацию новой фичи:

- матрица распределения транспорта, и закрепленных за ним водителей, по заявкам абонентов. Первый релиз фичи:
- ручное распределение транспорта из интерфейса приложения.
- визуально понятный формат вывода информации о задейстованном транспорте, времени работы (прогнозное), водителе, бригаде на транспорте, место выезда - место приезда - промежуточные точки
- доступ к матрице: admin, supervisor_zone0, supervisor_zone1
- Заявки абонентов — это новая сущность, приходят из n8n/внешней системы
- Водители - в зоне Транспорт, 4 человека. Справочник транспортных средств - новая сущность. Водитель ≠ ТС ≠ бригада
- supervisor_zone0 и supervisor_zone1 видят и редактируют только свою зону, admin — всё
- Формат матрицы не знаю. Нарисуй картинки с примерами - не менее 3 штук.
- для первой итерации Прогнозное время работы — вводится вручную при распределении заявки на ТС
- Промежуточные точки - полноценный маршрут с последовательностью остановок и временем между ними, но без условия обязательного заполнения промежуточных точек Дополнительно:

1. Транспорт - это zone_6, называется "Транспорт" в которой 4 человека: Покушев, Мелентьев, Нивин, Тимошкин. Найди ее. Отдельная сущность Водитель не нужна.
2. ТС и водители никак не делятся. Сущность ТС не привязана к водителям - в заявке выбираются в ручную. Админ видит и изменяет все, супервизоры - только свои зоны, но водителей и ТС все.
3. Параметры заявки - название/модель, госномер, населенный пункт нахождения, флаг «в строю»/"ремонт", «водитель по умолчанию» (подставляется при распределении, можно заменить)
4. супервизор выбирает сотрудников из своей зоны под конкретную заявку; водитель — отдельно от бригады; именованные бригады не нужны
5. Зона заявки определяется вручную при распределении. контракт payload для текущего релиза не требуется
6. статусы живут в приложении, push не в первом релизе
7. в первом релизе создавать/редактировать заявку ТОЛЬКО вручную в интерфейсе. создание и редактирование разрешены admin/супервизору своей зоны, с аудитом.
8. Жизненный цикл заявки: новая → распределена → в работе → выполнена (+ отменена). «выполнена/отменена» — вручную в матрице ставит создатель заявки + admin в любом случае
9. Неделя с почасовой шкалой (диспетчерская доска) и переключением дат. Диапазон рабочих часов на шкале 00:00 - 23:59
10. время локальное +05. Прогнозное время вводится как «начало + длительность (шаг 30 мин)». Сумма отрезков маршрута проверяется предупреждением, не блокирует
11. предупреждение + явное подтверждение, запись в аудит.
12. одна заявка = одно назначение (ТС + водитель + бригада + маршрут + время). Несколько заявок на одно ТС в течение дня подряд — можно. Заявка на несколько ТС сразу — можно.
13. viewer: вкладка доступна только на чтение.
14. сверка доступности водителя/бригады с матрицей отпусков и командировками - предупреждение.

**Предложение реализации фичи «Матрица распределения транспорта» (первый релиз)**

Неопределённость после ваших ответов: **≈ 0.05**. Всё критичное уточнено.

### 1. Сущности и модель данных (SQLite)

Новые таблицы (миграция `schema v15`):

SQL

```
-- Справочник ТС
CREATE TABLE vehicles (
  id              TEXT PRIMARY KEY,          -- genId('veh_')
  name_model      TEXT NOT NULL,             -- название/модель
  plate_number    TEXT NOT NULL UNIQUE,      -- госномер
  location        TEXT,                      -- населённый пункт нахождения
  status          TEXT NOT NULL DEFAULT 'in_service' 
                    CHECK (status IN ('in_service','repair')),
  default_driver_id TEXT,                    -- employee_id из зоны «Транспорт»
  created_at      TEXT,
  updated_at      TEXT,
  version         INTEGER NOT NULL DEFAULT 1
);

-- Заявки абонентов
CREATE TABLE subscriber_requests (
  id              TEXT PRIMARY KEY,          -- genId('sr_')
  title           TEXT,                      -- короткое название (опционально)
  vehicle_name    TEXT,                      -- название/модель абонента (если нужно)
  plate_number    TEXT,                      -- госномер абонента
  location        TEXT,                      -- населённый пункт
  status_flag     TEXT DEFAULT 'in_service'  -- 'in_service' | 'repair'
                    CHECK (status_flag IN ('in_service','repair')),
  default_driver_id TEXT,                    -- подставляется при создании назначения
  zone_id         TEXT,                      -- зона заявки (определяется вручную при распределении)
  status          TEXT NOT NULL DEFAULT 'new'
                    CHECK (status IN ('new','assigned','in_progress','done','cancelled')),
  created_by      TEXT NOT NULL,
  created_at      TEXT,
  updated_at      TEXT,
  version         INTEGER NOT NULL DEFAULT 1,
  external_id     TEXT                       -- заготовка под n8n
);

-- Назначения (отдельная сущность)
CREATE TABLE request_assignments (
  id              TEXT PRIMARY KEY,          -- genId('ra_')
  request_id      TEXT NOT NULL,
  vehicle_id      TEXT NOT NULL,
  driver_id       TEXT NOT NULL,             -- employee_id из зоны Транспорт
  brigade_ids     TEXT NOT NULL,             -- JSON-массив employee_id (любые зоны)
  start_at        TEXT NOT NULL,             -- локальное +05, 'YYYY-MM-DDTHH:MM'
  duration_min    INTEGER NOT NULL,          -- шаг 30 мин
  route_json      TEXT NOT NULL,             -- см. ниже
  status          TEXT NOT NULL DEFAULT 'planned'
                    CHECK (status IN ('planned','in_progress','done','cancelled')),
  created_by      TEXT NOT NULL,
  created_at      TEXT,
  updated_at      TEXT,
  version         INTEGER NOT NULL DEFAULT 1,
  FOREIGN KEY (request_id) REFERENCES subscriber_requests(id) ON DELETE CASCADE,
  FOREIGN KEY (vehicle_id) REFERENCES vehicles(id),
  FOREIGN KEY (driver_id)  REFERENCES employees(id)
);

-- Индексы
CREATE INDEX idx_ra_vehicle_time ON request_assignments (vehicle_id, start_at);
CREATE INDEX idx_ra_driver_time  ON request_assignments (driver_id, start_at);
CREATE INDEX idx_sr_status       ON subscriber_requests (status);
```

**Формат `route_json`**:

JSON

```
{
  "start": { "name": "Склад СЦ", "address": "..." },
  "end":   { "name": "г. Раменское", "address": "..." },
  "points": [
    { "order": 1, "name": "ТЦ Мега", "address": "...", "planned_duration_min": 30 },
    { "order": 2, "name": "...", "planned_duration_min": 45 }
  ]
}
```

Время между точками вводится вручную (шаг 30 мин). Сумма `planned_duration_min` сравнивается с `duration_min` назначения → только предупреждение + подтверждение + запись в `audit_log`.

### 2. Права доступа (RBAC)

|Роль|Видит матрицу|Создаёт/редактирует заявки|Создаёт/редактирует назначения|Меняет статусы `in_progress`/`done`/`cancelled`|
|---|---|---|---|---|
|admin|всё|да|да|да|
|supervisor_zone0|всё + только свою зону заявок|только zone0|только zone0|только свои заявки|
|supervisor_zone1|всё + только свою зону заявок|только zone1|только zone1|только свои заявки|
|viewer|всё (read-only)|нет|нет|нет|

- Водителей (зона 6 «Транспорт») и весь справочник ТС видят **все** роли.
- Бригаду супервизор выбирает из **любых** зон (включая свою и Транспорт).
- Зона заявки (`zone_id`) ставится вручную при создании/распределении.

### 3. API (первый релиз)

- `GET/POST/PUT/DELETE /api/vehicles.php`
- `GET/POST/PUT /api/subscriber_requests.php` (+ `?status=`, `?zone=`)
- `GET/POST/PUT/DELETE /api/request_assignments.php`
    - при POST/PUT: проверка перекрытий по `vehicle_id` и `driver_id` → warning (не блокирует)
    - проверка отпусков/командировок водителя + членов бригады → warning + confirm + audit
- `GET /api/transport_matrix.php?from=YYYY-MM-DD&to=YYYY-MM-DD` — данные для доски
- Все изменения пишутся в `audit_log` (actor, role, action, entity, details).

Заготовка под n8n: поле `external_id` + будущий endpoint `/api/subscriber_requests_n8n.php` (пока 501).

### 4. Жизненный цикл заявки

Текст

```
new → assigned (появилось ≥1 назначение)
    → in_progress (вручную создатель или admin)
    → done / cancelled (вручную создатель или admin)
```

Назначение живёт своей жизнью (`planned` → `in_progress` → `done`), но статус заявки меняется только вручную.

### 6. UX-потоки первого релиза

1. **Создание заявки** (admin / supervisor своей зоны)  
    Форма → сохранение → статус `new`. Аудит.
    
2. **Создание назначения**  
    Из матрицы или из карточки заявки → выбор ТС + водитель (по умолчанию подставляется) + бригада (мультиселект сотрудников) + маршрут + начало + длительность.  
    При сохранении:
    
    - проверка перекрытий ТС/водителя → warning
    - проверка отпусков/командировок → warning
    - сравнение суммы сегментов маршрута с duration → warning  
        Всё с явным подтверждением + audit.
3. **Матрица**  
    Вкладка «Матрица транспорта» (доступна всем ролям, viewer — read-only).  
    Переключение даты/недели. Клик по бару → карточка назначения. Drag-and-drop в v1 **не** делаем (только ручное редактирование).
    
4. **Смена статусов**  
    Только создатель заявки + admin.
